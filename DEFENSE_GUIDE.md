# Подготовка к защите ПР5 и ПР6

## Что это за проект

Сервис организации донорских мероприятий. Организация проводит мероприятия,
участник-донор записывается через регистрацию. У мероприятия есть дата, адрес,
лимит мест и статус, у участника — группа крови и контакты.

Исходная версия уже содержала dataclass-модели Organization, Event, Participant,
Registration, Enum, ООП-классы Person/Donor/Organizer/ContactManager, SQL-репозитории,
сервисы, JSON-обработчик, консоль и 49 тестов. Это соответствует предметной модели,
файловому вводу-выводу, тестированию и ООП предыдущих практических. Полное соответствие
ПР1–ПР3 не оценивалось: их методички не предоставлены.

Важная особенность именно этого репозитория: консоль использует PostgreSQL,
а JSON — отдельный демонстрационный набор. Веб ПР5/ПР6 читает только JSON.
Синхронизации JSON с SQL нет. Не говорите преподавателю, что прежняя консоль работала
только с JSON или что изменения в консоли автоматически видны на сайте.

## Что выполнено

**ПР5:** Django 5.2, конфигурация donor_site, пять приложений, маршруты и конвертер int,
view-функции, главная, четыре списка и четыре вида страниц деталей, Bootstrap,
общая page(), экранирование данных и 404. JSON преобразуется в прежние классы.
Состояние сохранено отдельным коммитом PR5; его код можно показать через git show.

**ПР6:** HTML вынесен в templates; общий base.html; extends, block, include;
контекст, for/empty, if; фильтры length/default/date; ссылки url с namespace;
CSS, JS и SVG через static. page() удалена из текущего веб-слоя. Источник JSON сохранён.
Отсутствующий объект передаётся как item=None в шаблон, render возвращает статус 404.

## Архитектура простыми словами

Браузер просит страницу. urls.py выбирает функцию. Функция читает JSON через
старый JsonHandler и адаптер, получает привычные объекты Python и передаёт их
в словарь контекста. Шаблон превращает данные в HTML. Браузер дополнительно
загружает CSS для оформления, SVG для логотипа и JS для года в подвале.

Пример запроса /events/1/:

```text
GET /events/1/
→ donor_site/urls.py: префикс events/
→ events/urls.py: <int:entity_id>/, entity_id = 1
→ events/views.py: detail(request, entity_id)
→ app/utils/web_data.py: load_catalog(), find_by_id()
→ app/utils/json_handler.py: JsonHandler.read_json()
→ data/sample_data.json → Event(event_date=date(...), status=EventStatus(...))
→ context = {"item": item, "organization": ..., "free_places": ...}
→ render(..., "events/detail.html", context, status=...)
→ events/detail.html extends base.html → include navigation/status
→ HTML в HttpResponse → браузер
```

Регистрации связываются по event_id и participant_id, мероприятие — по organization_id.
Классы прежние: их поля не заменялись Django-моделями. Для связи view ищет нужные
объекты и кладёт их в контекст. Catalog.free_places считает незакрытые отменой регистрации;
это число свободных мест, а не разрешение записаться на прошедшее/закрытое событие.
Дата и статус исходного мероприятия показаны как записаны в JSON; статус автоматически не меняется.

## Участки кода для показа

1. `events/urls.py`: `app_name = "events"`, два path с name=list/detail.
2. `events/views.py`: контекст и render со статусом 404 при item=None.
3. `app/utils/web_data.py`: `date.fromisoformat`, `EventStatus(...)`, `Event(**...)`.
4. `events/templates/events/list.html`: extends, length, for/empty, include with item=item only.
5. `events/templates/events/detail.html`: if item, date/default, связанные ссылки.
6. `templates/includes/status.html`: if/elif по status.value для подтверждения и отмены.
7. `templates/base.html`: load static, CSS/JS, include, block.
8. `homepage/static/homepage/js/main.js`: изменение textContent и data-updated-by.

Пример фактического подхода:

```python
item = find_by_id(catalog.events, entity_id)
context = {"item": item}
# events/detail.html содержит {% if item %} ... {% else %} ... {% endif %}
return render(request, "events/detail.html", context,
              status=404 if item is None else 200)
```

Это сокращённый фрагмент: в фактической view есть ещё организация и свободные места.

```django
{% extends "base.html" %}
{% block content %}
  {% for item in items %}
    {% include "events/includes/card.html" with item=item only %}
  {% empty %}
    <p>Пока нет данных.</p>
  {% endfor %}
{% endblock %}
```

`only` передаёт фрагменту только явно перечисленные переменные. Карточка ожидает item,
поэтому при включении с главной используется `with item=event only`.

## Дополнительная демонстрация регистраций и собственной 404

Исходные записи не подменяются вымышленными: в основном JSON регистраций нет.
Для показа двух состояний подготовлен отдельный учебный набор, явно помеченный
в примечаниях регистраций. Он строится из реальных организаций/доноров/мероприятия
проекта и двух добавленных учебных регистраций; в исходный файл ничего не записывает.

В отдельном терминале PowerShell из корня репозитория:

```powershell
.venv\Scripts\Activate.ps1
python tools/prepare_defense_data.py
$env:DONOR_JSON_FILE = "test-results/defense_data.json"
$env:DJANGO_DEBUG = "0"
python manage.py runserver 8001 --noreload --insecure
```

Открыть http://127.0.0.1:8001/registrations/: Подтверждено и Отменено.
Открыть /registrations/1/ и /registrations/2/, пройти по ссылкам до мероприятия и донора.
На /events/1/ будет 49 свободных мест: отменённая регистрация не занимает место.
Открыть /nonexistent/: общая собственная 404. `--insecure` нужен лишь локальному
серверу для раздачи static при DEBUG=False; для размещения его не используют.

После остановки сервера:

```powershell
Remove-Item Env:DONOR_JSON_FILE
Remove-Item Env:DJANGO_DEBUG
```

Следующий обычный запуск снова читает исходный JSON. Учебная копия лежит в
игнорируемом test-results. Редактирование этой копии отражается в следующем запросе.
Для пустого списка достаточно основного набора либо временно передать items=[] во view.

## Контрольные вопросы ПР5 — все 52 из раздела 8

Формулировки взяты из методички. Примеры Roomly в ответах адаптированы к донорскому сервису.

### 1. Что такое веб-приложение?

Программа, с которой взаимодействуют через браузер и HTTP; у нас это веб-просмотр донорских мероприятий.

### 2. Что такое фреймворк?

Готовая структура и средства разработки, управляющие выполнением приложения.

### 3. Что такое Django?

Веб-фреймворк Python: маршрутизация, ответы, шаблоны, ORM и другие компоненты. Здесь используется линейка 5.2.

### 4. Чем фреймворк отличается от библиотеки?

Библиотеку вызывает наш код; фреймворк сам вызывает наш код, например view при запросе.

### 5. Что такое Django-проект?

Общая конфигурация сайта. В нашем проекте это пакет donor_site.

### 6. Что такое Django-приложение?

Функциональная часть сайта: например events отвечает за мероприятия.

### 7. Чем Django-проект отличается от Django-приложения?

Проект объединяет настройки и приложения, приложение решает одну группу задач.

### 8. Для чего используется manage.py?

Для команд check, runserver, shell, findstatic с настройками конкретного проекта.

### 9. Для чего используется settings.py?

Для INSTALLED_APPS, middleware, шаблонов, языка, часового пояса, статики и пути JSON.

### 10. Для чего используется urls.py?

Для сопоставления адресов обработчикам: корневой urls делегирует адреса приложениям.

### 11. Для чего используется views.py?

Для view-функций, которые получают запрос, готовят данные и возвращают ответ.

### 12. Что такое development-сервер Django?

Локальный сервер для разработки и демонстрации: python manage.py runserver. Не сервер промышленного размещения.

### 13. Что такое HTTP?

Протокол обмена запросами и ответами между клиентом и сервером.

### 14. Что такое HTTP-запрос?

Сообщение клиента серверу, например GET /events/1/.

### 15. Что такое HTTP-ответ?

Сообщение сервера клиенту: статус, заголовки и тело, например HTML.

### 16. Из каких основных частей состоит HTTP-запрос?

Стартовая строка с методом/адресом/версией, заголовки и необязательное тело.

### 17. Из каких основных частей состоит HTTP-ответ?

Стартовая строка с версией/статусом, заголовки и тело.

### 18. Что такое URL?

Адрес ресурса; например http://127.0.0.1:8000/events/1/.

### 19. Что такое маршрут?

Правило сопоставления пути URL с обработчиком в urlpatterns.

### 20. Что происходит после обращения пользователя к URL Django-приложения?

Django выбирает маршрут, вызывает view, загружает данные и возвращает HTML-ответ браузеру.

### 21. Что такое HTTP-метод?

Тип действия с ресурсом: GET, POST и другие.

### 22. Чем GET отличается от POST?

GET запрашивает представление ресурса, POST отправляет данные для обработки. GET не должен менять состояние; здесь реализован просмотр.

### 23. Для чего используется path()?

Создаёт маршрут: path("<int:entity_id>/", views.detail, name="detail").

### 24. Что такое конвертер пути?

Проверяет и преобразует сегмент пути в значение Python, например int.

### 25. Для чего используется <int:id>?

Принимает неотрицательное целое из URL и передаёт его во view. У нас параметр называется entity_id.

### 26. Что такое view-функция?

Обработчик запроса: обычная Python-функция, например events.views.detail.

### 27. Какой параметр получает view-функция Django?

Первым аргументом получает HttpRequest (request); дополнительно — именованные параметры маршрута.

### 28. Что должна вернуть view-функция?

HttpResponse или его наследника. render() тоже возвращает HttpResponse.

### 29. Что такое HttpResponse?

Объект HTTP-ответа, содержащий тело, статус и заголовки.

### 30. Как передать параметр из URL в view?

Объявить <int:entity_id> в path и аргумент entity_id в detail(request, entity_id).

### 31. Зачем использовать имена URL-маршрутов?

Для построения ссылок по имени: events:detail. Путь можно менять без переписывания шаблонов.

### 32. Почему URL-маршрутизацию следует отделять от логики обработки данных?

Так адреса можно менять независимо от поиска данных, а обработчики легче читать и тестировать.

### 33. Что такое HTML?

Язык разметки структуры веб-страницы.

### 34. Для чего используется HTML-документ?

Описывает содержимое страницы, которое браузер отображает пользователю.

### 35. Из каких основных частей состоит HTML-документ?

Объявление DOCTYPE, html, head со служебными данными и body с содержимым.

### 36. Что такое HTML-элемент?

Участок разметки с тегом, атрибутами и содержимым, например <a href="...">Подробнее</a>. Бывают пустые элементы, например img.

### 37. Что такое CSS?

Язык оформления: цвета, размеры, отступы, сетки и адаптивность.

### 38. Для чего используются CSS-селекторы?

Выбирают элементы, к которым применяется правило: .entity-card выбирает класс карточки.

### 39. Что такое наследование стилей?

Некоторые свойства, например color и font-family, переходят от родителя к потомкам. Не все свойства наследуются.

### 40. Что такое Bootstrap?

Готовый CSS-фреймворк с сеткой, компонентами и утилитами.

### 41. Для чего используется Bootstrap?

Для быстрого оформления кнопок, карточек и базовой вёрстки. Подключён Bootstrap 5.3.3 через CDN.

### 42. Какие преимущества дает использование CSS-фреймворка?

Единообразные компоненты, адаптивность и меньше повторяющегося CSS.

### 43. Какая предметная область реализована в индивидуальном проекте?

Организация донорских мероприятий: организации, доноры, мероприятия и регистрации.

### 44. Какие страницы реализованы?

Главная; списки мероприятий, организаций, участников и регистраций; детали каждого типа; 404.

### 45. Какие URL соответствуют этим страницам?

/; /events/; /organizations/; /participants/; /registrations/; детали — соответствующий префикс и <int:entity_id>/.

### 46. Какие view-функции реализованы?

homepage.index и page_not_found; в четырёх предметных приложениях — list_view и detail.

### 47. Как запрос пользователя проходит от URL до HTML-страницы?

URLconf → view → JsonHandler → прежние dataclass → HTML. В ПР5 HTML собирала page(), в ПР6 его формируют шаблоны.

### 48. Какие элементы проекта были перенесены из консольного приложения ПР3?

Сохранены все классы, Enum, JsonHandler, сервисы, репозитории, консоль и 49 прежних тестовых проверок. Для веба добавлен JSON-адаптер.

### 49. Почему на ПР5 еще не выполняется полный переход на Django ORM?

Работа посвящена HTTP и веб-слою; методичка откладывает ORM. Наш старый SQL-код сохранён отдельно, веб читает JSON.

### 50. Как будет изменяться проект после подключения базы данных?

Загрузка и поиск перейдут на модели/запросы ORM, появятся миграции. URL и шаблоны можно сохранить, согласовав поля.

### 51. Какие данные пока используются для отображения страниц?

Записи data/sample_data.json: 2 организации, 2 донора, 1 мероприятие. Регистраций в исходном файле нет.

### 52. Какие возможности проекта будут реализованы на следующих практических работах?

Формы создания/редактирования, Django ORM, аутентификация и API. Это планы, а не уже выполненные функции.

## Контрольные вопросы ПР6 — все 30 из раздела 8

### 1. Для чего используются шаблоны Django?

Отделяют разметку и отображение данных от Python-обработчиков.

### 2. Почему формирование HTML -кода непосредственно в Python считается неудобным при развитии Django-приложения?

Смешиваются загрузка данных и разметка, общий HTML дублируется, изменения труднее проверять.

### 3. Для чего используется функция render()?

Соединяет шаблон и словарь контекста и возвращает HttpResponse с HTML и выбранным статусом.

### 4. Что такое контекст шаблона?

Словарь значений для шаблона: например {"items": catalog.events}.

### 5. Как передать из view в шаблон список объектов?

Передать словарь третьим аргументом render(request, "events/list.html", {"items": catalog.events}).

### 6. Для чего используются конструкции {{ ... }}?

Выводят значение переменной или атрибута: {{ item.title }}. HTML по умолчанию экранируется.

### 7. Чем {% if %} отличается от {% for %}?

if выбирает ветку, for перебирает коллекцию.

### 8. Для чего используется {% empty %}?

Выводит содержимое, если коллекция цикла пуста; у нас сообщение «Пока нет данных».

### 9. Что такое базовый шаблон?

Общий каркас страниц: templates/base.html с head, подключением ресурсов, навигацией и подвалом.

### 10. Для чего используются {% extends %} и {% block %}?

extends выбирает родителя, block задаёт области, которые дочерний шаблон переопределяет.

### 11. Для чего используется {% include %}?

Вставляет фрагмент шаблона, например карточку, навигацию или статус.

### 12. В каких случаях целесообразно выносить часть HTML в отдельный шаблон?

Когда фрагмент повторяется: events/includes/card.html используется на главной и в списке мероприятий.

### 13. Для чего используется параметр name в path()?

Задаёт стабильное имя маршрута, например detail.

### 14. Что такое app_name в urls.py?

Объявляет пространство имён приложения, например app_name = "events".

### 15. Зачем используются пространства имён URL?

Позволяют иметь list и detail в разных приложениях без конфликта: events:list, participants:list.

### 16. Чем отличается ссылка /rooms/ от {% url "rooms:list" %} с точки зрения организации Django-приложения?

Литеральный путь привязан к адресу; url строит путь по URLconf. Аналог проекта: {% url "events:list" %}.

### 17. Для чего используются фильтры шаблонов?

Форматируют вывод значения без изменения исходных данных.

### 18. Что делает фильтр length?

Возвращает количество элементов: {{ items|length }}.

### 19. Для чего используется фильтр date?

Форматирует date/datetime. У нас ISO-строка преобразована в date адаптером, затем date:"d.m.Y" даёт 15.10.2026.

### 20. Для чего нужен тег {% load static %}?

Загружает библиотеку тегов static для текущего шаблона.

### 21. Где должны храниться статические файлы Django-приложения?

В static/<пространство приложения>/; у нас homepage/static/homepage/{css,js,img}/.

### 22. Как подключить CSS-файл через систему static files?

После load static: <link rel="stylesheet" href="{% static 'homepage/css/style.css' %}">.

### 23. Как подключить изображение к шаблону?

<img src="{% static 'homepage/img/logo.svg' %}" alt="Логотип">.

### 24. Как подключить JavaScript-файл?

<script src="{% static 'homepage/js/main.js' %}" defer></script>. Скрипт обновляет год в подвале.

### 25. Почему собственный CSS проекта не следует полностью заменять подключением Bootstrap?

Bootstrap даёт общие компоненты; собственный CSS задаёт оформление донорского сервиса, сетки и статусы. Он обязателен по ПР6.

### 26. Какие задачи должны выполняться во view, а какие – в шаблоне?

View получает данные, ищет объект, готовит контекст и HTTP-статус. Шаблон формирует разметку, циклы и визуальные условия.

### 27. Почему бизнес-логику не следует переносить в Django-шаблоны?

Правила должны независимо тестироваться и применяться в разных интерфейсах. Подсчёт мест находится в Catalog.free_places(), не в HTML.

### 28. Почему в ПР6 данные по-прежнему загружаются из JSON, а не из Django ORM?

Это условие этапа ПР6: меняется представление, источник данных остаётся JSON. Django ORM будет отдельным этапом.

### 29. Чем архитектура веб-части проекта после ПР6 отличается от архитектуры ПР5?

ПР5: JSON → объект → HTML-строки → page → HttpResponse. ПР6: JSON → объект → context → render → template → HttpResponse.

### 30. Для чего в ПР6 необходимо отказаться от функции page()?

Чтобы общий HTML жил в base.html, а view занимались данными. page() удалена после перевода всех страниц; версия ПР5 доступна в Git.

## Частые ошибки и короткие ответы

- Вернуть из view строку: Django ожидает HttpResponse; обычная строка нарушит контракт.
- Обратиться к item.title при item=None в Python: AttributeError. Проверка обязательна.
- Вывести «Не найдено» со статусом 200: текст есть, но HTTP-семантика ошибочная.
- handler404 внутри urls.py приложения: Django читает его только в корневом URLconf.
- DEBUG=False и нет ALLOWED_HOSTS: реальные запросы будут отклоняться.
- DEBUG=False и пропала статика: runserver обычно не обслуживает её в этом режиме;
  для местной демонстрации --insecure, для размещения — collectstatic и отдельная раздача static.
- Забыть зарегистрировать приложение: его шаблоны и static не обнаружатся через загрузчики приложений.
- Забыть load static в include: библиотека тегов загружается для каждого файла отдельно.
- Не совпало имя url: NoReverseMatch; проверить app_name, name и переданные параметры.
- Исчезло значение в HTML без исключения: проверить имена ключей контекста и атрибутов.
- JSON не найден/повреждён: ошибка чтения не замалчивается пустым списком; проверить путь и JSON.
- Не смешивать статус Event PLANNED и статус Registration CONFIRMED: это разные Enum.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1

python manage.py check
```

Без активации заменить python на `.venv\Scripts\python`.

`makemigrations`/`migrate` нужны при появлении Django ORM, а в ПР5/ПР6 не требуются.

```powershell
git status
git diff
git diff --check
git log -5 --oneline
git show 15791ad:homepage/views.py
git show --stat 15791ad
```

`git -c user.name=sksk-a commit ...`; email взят из существующей конфигурации.
